# Lesson Spec: Weather Station Project (Project 1)

Status: Draft for review. No dataset or student code exists yet.

## Purpose

Students solve a weather analysis problem by retrieving data from a database and applying conditionals, loops, and functions. The project is built as four levels. Each level teaches one skill and has its own automated tests. Level 4 combines the earlier levels into the full solution.

This lesson is the first project in a set. Later projects should use the same structure (see "Reuse for later projects"), so this spec defines a template, not a one-off.

## Student Problem

A weather station recorded daily readings for one year. A meteorologist asks the student to write a report for one station and one date range. The report must:

- Count heat-wave days and heavy-rain days.
- Report total rainfall, the highest daily temperature, and the number of normal days.
- Return the list of flagged days in date order.

## Dataset

Synthetic data generated by a script with a fixed random seed, so every run produces the same file. No real station or personal data.

SQLite database `weather.db`, table `daily_readings`:

| Column | Type | Meaning |
|---|---|---|
| station_id | TEXT | Station code, e.g. `ST-A`, `ST-B`, `ST-C` |
| date | TEXT | ISO date, `YYYY-MM-DD` |
| temp_high_c | REAL | Daily high, °C |
| temp_low_c | REAL | Daily low, °C |
| rain_mm | REAL | Rainfall in millimeters |

Size: 3 stations × 365 days = 1,095 rows. A small, fixed set of rows will be hand-checked so tests have known answers.

## Classification Rules (given to students)

These thresholds are part of the problem statement. Students do not choose them.

- **Heat wave:** `temp_high_c >= 35.0`
- **Heavy rain:** `rain_mm >= 20.0`
- **Normal:** neither of the above. A day can be both heat wave and heavy rain. In that case it counts as a heat wave and as heavy rain.

## Levels

### Level 1: Retrieve Data from the Database (SQL and function)

**Student task:** Write `get_readings(conn, station_id, start_date, end_date)` that returns the matching rows as a list of dictionaries, sorted by date.

**Skill:** Querying a database with parameters; reading returned rows.

**Tests:**
- Returns only rows for the requested station.
- Returns only dates from `start_date` to `end_date`, inclusive on both ends.
- Rows are in ascending date order.
- An empty date range returns an empty list, not an error.
- Uses parameter placeholders, not string formatting (a code review check, not an automated test).

### Level 2: Make Decisions (conditionals)

**Student task:** Write `classify_day(row)` that returns a list of labels for one reading: `"heat_wave"`, `"heavy_rain"`, or `"normal"`. A day with both conditions returns `["heat_wave", "heavy_rain"]`.

**Skill:** `if`/`elif`/`else` logic; boolean conditions; boundary values.

**Tests:**
- Temperature exactly 35.0 is a heat wave; 34.9 is not.
- Rainfall exactly 20.0 is heavy rain; 19.9 is not.
- A day with both conditions returns both labels.
- A day with neither condition returns `["normal"]`.

### Level 3: Process Every Record (loops)

**Student task:** Write `summarize(readings)` that loops over a list of classified readings and returns a dictionary:

```
{
  "heat_wave_days": int,
  "heavy_rain_days": int,
  "normal_days": int,
  "total_rain_mm": float,
  "max_temp_c": float,
  "flagged_dates": [str, ...]   # dates with any label other than "normal", in date order
}
```

**Skill:** `for` loops; accumulators; tracking a maximum.

**Tests:**
- Counts match a hand-checked small input.
- `total_rain_mm` is the sum of all rainfall, rounded to 1 decimal place.
- `max_temp_c` is the highest `temp_high_c` in the input.
- An empty input returns zeros and an empty `flagged_dates` list.
- A check that the code uses a loop, not a built-in aggregate shortcut such as `sum()` or `max()`, is optional and the team should decide whether to include it. (Open question below.)

### Level 4: Solve the Full Problem (functions working together)

**Student task:** Write `build_report(conn, station_id, start_date, end_date)` that calls the functions from Levels 1 to 3 in order and returns the summary dictionary.

**Skill:** Defining functions; passing values between them; combining small functions into a larger solution.

**Tests:**
- Output matches a known-good report for station `ST-A` over January 2026 (expected values stored with the tests).
- Output for a different station and range matches its expected report.
- The function does not modify the database.
- Calling `build_report` twice with the same arguments returns the same result.

## Feedback and Fallback

- Each test failure returns a plain-language message tied to the level, for example: "Level 2: a temperature of 35.0 should count as a heat wave."
- Hints are given per level, in order, after a failed attempt. Hints do not reveal the solution.
- If the automated grader cannot run a student's code (for example, a syntax error), the student sees the error and a hint. They are not blocked from the next level's instructions.
- Non-adaptive fallback: the four levels run in a fixed order. The adaptive routing (see the vision document) can skip or repeat levels later, but the fixed order is always available.

## Grading and Mastery

- Each level passes when all its tests pass.
- A level counts toward mastery when the student passes it on the first or second attempt. The threshold and the number of attempts are open questions for the team.
- Mastery evidence per level feeds the stage model for the concept that level targets.

## Reuse for Later Projects

Each project is a folder with the same parts, so new projects don't require new engine code:

```
projects/<project-name>/
  manifest.yaml      # title, levels, concept mapping, standards codes
  dataset/           # generator script and fixed seed
  levels/            # one folder per level: instructions, hints, tests
  reference/         # reference solution, used only to check the tests
```

The first project is the template. Project 2 should reuse the same engine and only change the dataset, instructions, and tests.
